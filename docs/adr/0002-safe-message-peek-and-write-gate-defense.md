# 消息默认无损采样与生产级安全防护体系

## 背景与问题陈述 (Context)

大语言模型（LLM）与自主 Agent 在面对复杂消息系统运维排障时具有不确定性：
1. **消息误删灾难**：在 RabbitMQ 中，执行 `basic_get` 或 `basic_consume` 时若默认回复 ACK，在途未消费的消息将从队列中被物理永久删除；
2. **高危指令误触**：模型若在未明确影响范围前直接发起清空队列 (`purge_queue`) 或删除交换机 (`delete_exchange`)，将引发灾难性业务中断；
3. **敏感凭据外泄风险**：连接串包含的密码、数据库 Secret 若在 JSON-RPC 工具返回中明文暴露，极易进入模型上下文并导致凭证泄漏。

## 架构决策 (Decision)

我们决定构建全方位、多纵深的**四重安全防护体系**：

1. **默认零损采样 (Zero-Loss Peek)**：
   - 消息探查默认实施 `basic_get(no_ack=False)` 窥探；在异步上下文退出阶段，统一延迟批量执行 `reject(requeue=True)`，保证队列消息数量与顺序完全零破坏；
   - 对非 UTF-8 二进制载荷自动编码为 Base64 安全回传，防止解码崩溃。
2. **强只读写保护门禁 (Write Gate Defense)**：
   - 服务端启动默认处于强只读保护状态（`allow_write=False`）；
   - 任何涉及拓扑声明、清空、删除队列/交换机及消息发布的写操作，在执行前必须通过门禁检查；未显式传 `--allow-write` 时立即阻断并抛出清晰的结构化业务错误。
3. **高危指令二次确认机制 (Double Confirmation)**：
   - 对 `purge_queue`、`delete_queue` 与 `delete_exchange` 等高危动作，入参强制约束 `confirm: bool = False`；
   - 当调用方未显式传入 `confirm=True` 时，底层仅执行元数据探测并返回受影响的消息数或拓扑范围预估报告，绝不执行物理删除。
4. **全域凭据与错误脱敏引擎 (Credential Masking)**：
   - 任何涉及 URL 协议串、字典属性（含 password/token/key）或包含 URL 的底层网络异常堆栈，在序列化为 MCP 响应前必须经由脱敏引擎将明文密码替换为 `***`。

## 方案权衡 (Considered Options)

- **方案 A: 依赖模型自主防护（无代码级门禁）**
  - *优点*：代码实现极简；
  - *劣势*：极度不可控，模型单次幻觉即可能抹除整个生产队列。
- **方案 B: 绝对只读（彻底禁止一切写与确认操作）**
  - *优点*：绝对安全；
  - *劣势*：使智能体丧失了死信重放、队列修复与自愈运维能力，沦为纯看板工具。
- **方案 C: 默认零损探查 + 强只读门禁 + 二次确认 + 全域脱敏（已采纳）**
  - *收益*：兼顾绝对安全底线与受控的主动运维能力，彻底杜绝误操作与凭据泄漏。
